# Mirth 客户端核心规格调查

调查日期：2026-11-16。本文是研究结果与设计建议，不是已批准的 core-spec，也不表示任何客户端功能已经实现。

## 1. 已确认的产品约束

- Matrix 网页客户端，以 Telegram Web K 为交互参考。
- Cinny v4.12.8 是用户确认的功能对标基线，不以开发分支计划作为基线。
- 界面小巧精干、高性能、轻量，支持多端和响应式布局。
- 用户写作“WPA”，本文暂按 PWA 理解；不据此推断需要原生客户端或桌面封装。
- 轻量不能通过删掉 Cinny 已有功能兑现。模块延迟加载不等于产品功能延期或缺失。
- 中文为沟通、文档、注释、提交说明的主要语言；标识符与技术名称保留原文。

## 2. 证据与结论边界

证据分为规范事实、源码事实、实际观察、设计推论、待验证。

- 规范基线为 Matrix v1.19；调查时 latest 指向该版本。[M1]
- 已读取 Client-Server API 目录，重点调查认证、同步、房间、关系、空间、加密、媒体、通知和通话。[M2]
- 未穷尽所有 Matrix 事件、MSC 和服务器内部实现。Server-Server、Application Service、Identity Service、Push Gateway 需要按客户端影响继续核对，不能宣称“理解全部特性”。
- Cinny 稳定目录用于建立功能候选清单；目录或导入存在不等于该功能完整可用。下表明确区分直接读过的实现与仅定位的入口。
- 实际浏览器观察 Web K 登录页：二维码登录、手机号登录、Passkey、简体中文入口、深色模式。未登录，未实测消息、通话、触摸操作或性能。
- Web K 登录后行为的依据是公开源码，不是实际登录体验。
- 尚无 Mirth/Cinny/Web K 的同条件性能测量；不声称任何框架或方案更快。

## 3. Matrix 能力覆盖与组件影响

稳定协议、被接受的 MSC、正在讨论的 MSC、SDK 实现、服务器支持是独立维度。规范中的可选功能也可能是本产品的必需功能。

| 能力域 | 必须调查的内容 | 对核心规格的影响 | 当前证据 |
|---|---|---|---|
| 发现与认证 | homeserver 发现、版本与能力、密码/SSO、OAuth、UIA、注册、重置密码、刷新、软退出 | 登录流程按服务端能力选择；会话与视图分离；软退出不能等同清空设备 | v1.19 认证章节 [M2] |
| 用户与设备 | 全局/房间资料、设备会话、第三方标识、账户管理、屏蔽 | 用户标识不可用昵称代替；全局资料与房间资料分别建模 | [M2] |
| 同步与存储 | 首次/增量同步、断线补齐、limited 缺口、to-device、state_after、缓存迁移 | SDK/同步层负责协议语义；UI 不自行拼接原始响应；游标与事件应用一致 | [M2][M3] |
| 房间生命周期 | 创建、邀请、加入、敲门、拒绝、离开、踢出、封禁、忘记、升级、别名、发现 | 加入前资料不完整；升级有前驱/后继；只读与成员身份分别表达 | [M2] |
| 权限与治理 | power levels、加入规则、历史可见性、举报、屏蔽、策略及管理接口 | 动作能力会变；显示按钮不代表有权限；拒绝后需更新状态 | [M2] |
| 消息与事件 | 文本/富文本、媒体、状态事件、自定义与未知事件、撤回 | 不可信内容要校验和清洗；未知事件不能使时间线崩溃 | [M1][M2] |
| 事件关系 | 回复、编辑、反应、线程、聚合、回执 | 回复不等同线程；本地回显需与远端事件去重；线程回执有独立作用域 | [M2] |
| 未读与临时状态 | 已读/私有回执、完全已读位置、手动未读、输入、在线状态 | 不能合成一个 unread 布尔值；隐私设置和服务器能力会影响显示 | [M2] |
| Spaces | 多父级、子空间、层级分页、循环、权限、顺序、受限加入 | Space 不是 Telegram 文件夹；不能假设严格单父树或单一所有者 | [M2] |
| 加密 | Olm/Megolm、设备信任、交叉签名、验证、SSSS、备份、导入导出、历史分享 | 不可解密与加载失败分开；恢复、设备验证、信任变化是独立流程 | [M2][M3] |
| 媒体 | 上传、大小限制、进度/取消、鉴权、缩略图、加密附件、重定向 | 统一媒体访问边界；图片 URL 转换不代表请求已鉴权；缩略图也涉及隐私 | [M2][M3] |
| 搜索 | 房间/用户发现、服务端消息搜索、加密正文、本地索引、分页 | 服务端不能凭空搜索加密正文；本地结果必须显示覆盖范围 | [M2]，索引设计为推论 |
| 通知 | push rules、pushers、提及、静音、解密后通知判断、浏览器通知与 Web Push | Matrix 推送与浏览器推送不是同一环节；需网关、权限与设备能力 | [M2][P1][P3] |
| 通话 | 稳定一对一 VoIP、TURN、MatrixRTC、LiveKit、设备权限、来电、多设备、后台限制 | 独立资源生命周期；按能力展示不可用原因；不能因协议未稳定就删除 Cinny 对应能力 | [M2][M5][C5] |
| 扩展生态 | 桥接、机器人、应用服务、identity、widgets、投票、位置、语音及自定义事件 | 分别核对规范/MSC/实现；不得将 Element 特性直接当作所有 Matrix 客户端特性 | 尚需逐项追踪，未完成 |

## 4. Cinny v4.12.8 功能下限

版本来源为官方 latest release API，发布标签 v4.12.8，提交 1e6412ed5b639607a8c7485f7d0b447f073fa09c。[C1]

| 功能组 | 已得到的证据 | 调查状态 |
|---|---|---|
| 外观与密度 | 系统主题、单色、缩放、消息布局/间距、日期时间、成员/资料事件过滤、隐藏事件 | 已核对设置项，未运行验证 [C2] |
| 编辑器 | 富文本编辑、Markdown、提及补全、命令、表情贴纸、房间草稿、回复草稿、输入法组合态处理 | 已读关键源码前段；需逐操作验收 [C3] |
| 附件 | 文件选择/粘贴/拖放、加密、上传取消；图片/视频/音频/文件、缩略图、BlurHash、剧透 | 已读输入流程关键段与完整内容构造实现 [C3][C4] |
| 时间线 | 虚拟分页、时间线片段、事件定位、编辑/反应/回复、未知/撤回/未解密渲染入口 | 已读关键实现；完整边界待实测 [C6] |
| 通话 | 来电、接受/拒绝/忽略、通话嵌入、LiveKit 与 WebRTC 能力、权限判断 | 已读关键实现；不等于所有服务器可通话 [C5] |
| 媒体与隐私设置 | 禁止媒体自动加载、普通与加密房间 URL 预览、隐藏输入与已读状态 | 已核对设置项 [C2] |
| 登录/注册/重置密码 | auth 页面及表单入口 | 已定位稳定源码，流程完整性待核对 [C7] |
| 房间、空间、发现、邀请、收件箱 | 创建、层级、大厅、搜索、通知与邀请页面 | 已定位稳定源码，不能据目录声明完整支持 [C7] |
| 安全与设置 | 设备、验证、恢复、secret storage、成员/权限、图片包、开发者工具 | 已定位稳定源码，需补齐行为场景 [C7] |
| 线程、搜索范围与后台推送 | 不能从 ThreadIndicator 导入、搜索目录或 manifest 推断完整能力 | 未确认，必须单独核验 |
| PWA | manifest 有 standalone、start_url、图标与 portrait 配置 | 仅证明配置存在；不证明离线、推送或多平台表现 [C8] |

功能对齐的验收单位应是“用户可以完成的操作和异常恢复”，而不是相同菜单名称或文件数量。上表仍不是完整 Cinny 功能清单；发布 Mirth 前需要逐项闭合，不允许默认将未核验项目排除。

### 4.1 补充核验：不要高估或低估 Cinny

- 已直接读取 `useMessageSearch.ts`：调用 `mx.search`，带房间、发送者、排序与分页过滤。该路径没有本地加密正文索引；不能据“至少 Cinny”推导出必须额外实现全量加密搜索，也不能据此断言整个仓库不存在其他搜索实现。
- 已直接读取 `SystemNotification.tsx`：包含桌面通知权限、通知声音，以及 email 类型 pusher 的设置/注销。此处不是 HTTP Web Push 的注册实现，不能将邮件通知、前台桌面通知、关页推送混为一项。
- 已读取房间与空间通用设置的组合：房间资料、加入规则、发布到目录、地址、升级；普通房间另外包含历史可见性与加密设置。
- 设备与账户源码核对到设备改名/退出、OIDC 设备管理跳转、设备验证、口令保护的加密密钥导入导出、用户资料与屏蔽列表；不能把“消息数据导出”的文案解释为全部消息正文备份。
- 邀请页面区分 Primary、Public、Spam，提供接受/拒绝与批量拒绝；通知收件箱支持筛选与标记已读。这些属于功能下限，不应只保留一个总未读徽标。
- 登录工具核对到服务器发现与版本校验、服务器允许列表、停用账户、限流、登录后返回原路由。注册与密码重置的实际表单及错误提示也已定位；服务端策略决定是否可用。

上述补充文件均位于 [C7] 对应的固定标签下；它们增加源码证据，不替代浏览器功能验证。用户尚未授权超出 Cinny 的附加能力，也未授权删除其已有能力。
## 5. Telegram Web K：借鉴交互，不复制协议模型


源码调查参考提交 2e4bbb52b6aec5e95ee32e5c2882c1f05de32200。[T1]

| 可借鉴方向 | 源码入口 | 迁移限制 |
|---|---|---|
| 列表—会话—详情的布局及窄屏单列切换 | appImManager、appColumns、sidebarLeft、sidebarRight | 房间/事件/线程需要可深链路由；临时弹层不能替代浏览器历史 [T2] |
| 增量会话列表与时间线视口切片 | autonomousDialogList、appDialogsManager、chat/bubbles | Matrix 历史缺口、解密、编辑、撤回、回显去重不能交给 DOM 层 [T3] |
| 媒体延迟加载与离屏动画暂停 | chat/bubbles 及媒体队列 | 需额外处理鉴权、附件解密、缓存身份隔离 [T3] |
| 渐进披露与设置搜索 | sidebarLeft/tabs/settings、lib/settingsSearch | 紧凑不能变成只有右键/悬停才可发现；移动端须有等价入口 [T4] |
| 编辑器辅助状态与附件流程 | chat/input | 不复制 Telegram 富消息模型；保留 Cinny 富文本能力，不擅自降成纯文本 [T5] |

Web K 的实现同时包含控制器、手写 DOM 和组件；视觉简洁不等于内部结构小。建议借鉴分页、离屏暂停和逐层返回体验，不照搬大型时间线/编辑器控制器。

Telegram 文件夹不等于 Space，论坛话题不等于 Matrix thread，Telegram 联系人/服务器搜索也不等同 Matrix 用户目录与加密消息搜索。

## 6. Web/PWA 多端边界

- 可安装、独立窗口、离线壳、离线数据、后台同步、Web Push、分享入口是不同能力。[P1]
- 后台同步缺少支持时，应明确“待发送”，在恢复前台/连接后继续，而非伪造已发送。[P1]
- iOS/iPadOS 16.4 引入主屏幕 Web App 推送；权限请求需要直接用户操作。这是功能引入证据，不是当前所有版本的实测保证。[P3]
- 默认存储可能被驱逐；隐私模式、配额不足、持久化申请被拒绝都需处理。不能将消息/媒体缓存清理与加密密钥库清理混为一谈。[P2]
- SDK 警告：多个 MatrixClient 同时访问同一加密 IndexedDB 可能导致损坏和解密失败。多标签页的所有权与故障转移需要进入运行时规格。[M3]
- 响应式必须覆盖窄屏、平板横竖屏、桌面、软键盘、安全区、200% 缩放、触摸和键盘。具体断点需以内容和原型验证，不预先复制 Web K 的像素值。
- 手机/平板视图改变的是布局，不应重建会话、清空草稿、打断通话或重复初始化加密。

## 7. 性能：先定义测量，再选实现

当前只给测量维度，不填未经测试的性能数字。

| 维度 | 必须固定的条件与场景 |
|---|---|
| 首次可交互 | 设备、浏览器、网络、冷缓存；登录壳、首次同步、首个可读会话分别计时 |
| 房间切换 | 缓存命中与未命中、明文与加密、含媒体与纯文本分别测量 |
| 滚动 | 长历史、可变高度图片、解密后高度变化、向上分页、跳事件后返回位置 |
| 编辑 | 中文输入法、长草稿、粘贴富文本、附件队列、不被其他房间更新干扰 |
| 内存 | 房间数量、缓存窗口、多次切换、媒体关闭、离开通话后的回收 |
| 后台与流量 | 隐藏标签页、跨标签同步、断线恢复、媒体自动加载开关 |
| 资源体积 | 压缩后传输量、解压后 JS、WASM、字体、表情、通话与搜索模块分开统计 |

候选策略：列表虚拟化、增量订阅、有界缓存、重模块按需加载、媒体并发上限、资源释放。是否使用 Worker、用几个、哪些任务迁移，以 SDK 约束和原型测量决定；不把“所有加密必须由自建 Worker 执行”伪装成协议要求。

不重新实现 SDK 已提供的协议状态机，也不为了隔离 SDK 而复制一整份可变房间/事件对象图。

## 8. core-spec 的候选组织方式

| 方案 | 优点 | 风险 |
|---|---|---|
| 只按页面写规格 | 易与原型对应 | 同步、权限、信任、草稿和生命周期容易散落 |
| 只按协议服务写规格 | 边界清楚 | UI 组件交互、密度和响应式无明确契约 |
| 按用户能力追踪，组件与运行时契约分层（建议） | 功能不丢失，组件可独立验收，跨切状态有归属 | 需要维护能力到契约/场景的映射 |

建议结构，尚待批准：

1. 产品能力与 Cinny 对标矩阵：每个能力有稳定标识、来源、前置条件、支持状态、验收场景。
2. 全局交互原则与设计 token：密度、主题、焦点、动效、错误反馈、触摸目标；不在业务组件硬编码。
3. 应用壳与导航：房间/事件/线程路由，空间上下文，详情与临时层，窄屏返回与焦点恢复。
4. 组件契约：列表项、时间线、消息、编辑器、上传、搜索、详情、设置、安全流程、通话等。
5. 运行时契约：会话、同步、SDK 适配、加密/信任、媒体、存储、通知、通话及平台能力。
6. 验收与性能场景：功能对齐、异常恢复、响应式、可访问性与资源预算。

每个组件必须说明：职责/非职责、输入、输出意图、状态所有者、加载/空/失败/权限不足状态、组合关系、键盘与触摸、响应式、资源生命周期、可观察验收结果。

协议服务不直接控制弹窗；展示组件不自行建立 MatrixClient；权限/信任判断不由每个按钮独立猜测。单一状态所有者并不意味着所有状态都进入一个全局 store。

## 9. 风险与尚未闭合事项

1. Cinny 全功能逐路径核验尚未完成；目前不能宣称“功能对齐规格已完整”。
2. 登录后的 Web K 交互只有源码证据，缺少授权登录环境下的视觉/操作验证。
3. SDK、同步策略、RTC/LiveKit、加密历史分享的版本兼容需要锁版本原型；尚未选定前端框架。
4. 用户没有授权削减通话、富文本、图片包等功能，不能以轻量为由擅自延期。
5. MatrixRTC 与 Sliding Sync 的成熟度变化快，正式规格落地时须重新核对。
6. Web Push 涉及服务端网关与运维；单个前端 manifest 不能完成。
7. 许可：Web K 为 GPL-3.0-only，Cinny 为 AGPL-3.0-only。[T6][C9] 借鉴交互与复制代码/资源是不同决策；实际复用需逐文件核对许可与项目 LICENSE，不因开源就默认可直接搬用。本报告不是法律意见。
8. 调查范围还须补齐扩展生态与 Cinny 待核验项目，之后才可冻结最终 core-spec。本文允许讨论架构方向，不允许据此宣布实现范围完整。
